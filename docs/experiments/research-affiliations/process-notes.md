# Process notes: what the method and its skills got right, missed, or should flag

Written as the experiment runs, not reconstructed afterwards. Each note says where it happened, what happened, and
what to change. The user asked for this alongside the deliverable: a simple semantic layer for the three approved
questions, plus conclusions to improve the skills. Method frozen at `05428c5`; changes proposed here are not applied
to the skills during the experiment (they would count as method changes).

Severity: **important** (can make a result wrong or unverifiable), **gap** (missing guidance that cost time or a
decision), **minor** (friction).

| # | Step and skill | What happened | Severity | Proposed change |
|---|---|---|---|---|
| 1 | Inspection, `inspect-sources` | The bounded set was estimated at "about 200 strings" by counting only strings that mention Argentina; the approved questions cover every affiliation, so the real set has 962. Caught at the draw, after scope approval. | important | `inspect-sources`: size the set in the **unit the questions count** (here, every affiliation of the selected works), and show reviewer workload before scope approval. |
| 2 | Inspection, `inspect-sources` | The first probe mixed raw and normalized string counts, kept one organization per shared acronym, and read e-mail domains as evidence. The reviewer caught all three. | important | `inspect-sources`: state the counting unit of every number; strip contact data before any name probe; index acronyms to sets. A reviewer step was essential, keep it mandatory. |
| 3 | Inspection, `inspect-sources` | The first capture of a live API (Crossref) had no request ledger, so it could not be reviewed; a re-capture was needed. | gap | `inspect-sources`: for live APIs, capture with a request ledger from the start (query, pages, totals, termination, hashes). |
| 4 | Initialize, `start-domain` | `method.py experiment --init` records `git HEAD` as the frozen method version, so it must run before committing anything else. The skill does not say so. | gap | `start-domain`: say "initialize the log before your first commit", or let `--init` take the method commit explicitly. |
| 5 | Initialize, `start-domain` | The skill says both "omit capabilities not built" and "declare `method.app` for new domains"; declaring it requires an app file that does not exist yet. Resolved by omitting it. | minor | `start-domain`: declare `method.app` when the app step starts. |
| 6 | Initialize, `start-domain` | Ontop does not start with an empty mapping (the skill anticipates this). Runtime readiness can only be checked after the first mapped term. | minor | Keep as is; optionally a minimal placeholder mapping so the service health can be checked at initialization. |
| 7 | Experiment log | Session times, hours and interventions are edited by hand in YAML. Two errors in this run: a duplicated `reason` key (silently keeps only the last value) and an end time written before the work ended. Both caught and fixed. | important | A small command to open and close sessions and append interventions (`method.py experiment <domain> --start/--stop/--note`), and `--check` should reject duplicate keys. |
| 8 | Questions, `add-question` and lifecycle | The approval record has one `reviewer`. In this experiment the person who approves business definitions (the user) and the person who adjudicates references (a named reviewer, still pending) are different roles. | gap | Contracts: name both roles, the business owner for requirements and the reference reviewer for evidence; the lifecycle should not let one stand in for the other. |
| 9 | Sources, `add-source` | The skill assumes the loader downloads its data. Here the loader must load the **approved snapshot** from the inspection, because a fresh request to a live API is a different snapshot. | gap | `add-source`: when an inspection snapshot was approved, load that snapshot and check its fingerprint; never re-download silently. |
| 10 | Sources, `add-source` | Step 1 asks a person to approve a source profile, which the inspection and the scope approval already covered. Reused, as the contracts allow. | minor | `add-source`: say explicitly that an approved inspection profile satisfies step 1. |
| 11 | Sources, `add-source` | The loader recorded `load_run` but the source manifest was edited by hand, so the manifest did not prove what a load used. GPT caught it. | important | `add-source`: the loader writes or checks the domain's source manifest after a committed load, with every input fingerprint (here also the DOI list). Never by hand. |
| 12 | Sources, `add-source` | Multi-valued source fields were flattened (ROR locations: only the first kept). No Argentine organization was lost in this release, but the loader did not implement the approved "any location" definition. | important | `add-source`: keep multi-valued fields in their own table, or document the flattening and check it against the approved definitions. |
| 13 | Sources, `add-source` | Database credentials were interpolated into a connection string. Several older loaders do the same (energy, CSL, ChEMBL, and the Wikidata loader written in this session). | minor | `add-source`: pass credentials as connection keyword parameters; fix the older loaders when they are touched. |
| 14 | Review loop | Every stage so far had a second assistant review it (inspection, revision, scaffold, loader). It caught 8 real defects; none was caught by the automated checks. | important | Keep an independent reviewer after each stage as part of the method, and record what it catches; the automated gates do not replace it. |
| 15 | Mapping, `map-source` | Ontop did not start: its SQL parser treats `WORK` as reserved, so `FROM crossref.work` failed to parse and the IRI column was "not found". The log line that mattered was an INFO line («FAILED TO PARSE»), not the final error. | gap | `map-source` watch-outs: when Ontop says a placeholder is missing, look for «FAILED TO PARSE» first; quote table names that are SQL keywords (or avoid them in `schema.sql`). |
| 16 | Mapping, `map-source` | The user asked to see the actual dictionary (the Turtle draft) before approving; the skill only asks for a table of terms. | important | `map-source`: present the draft ontology text with labels and comments together with the table; approval is of the terms as they will be written. |
| 17 | Mapping, `map-source` | Mention IRIs built from a DOI percent-encode its slash (`10.1001%2F...`). Valid and stable, but not pretty; publication IRIs use the DOI resolver instead. | minor | Note in `map-source` that identifiers with slashes are encoded in templates; prefer an existing resolver IRI where one exists. |
| 18 | Questions to links, `add-question` and `link-entities` | cq2's approved definition says "only identifications accepted by the reviewer count", mixing the system's link status with the reference reviewer's judgment, who must stay blind to the system's links. Caught while proposing links. | important | `add-question`: keep the system's definition (what Rastro counts) separate from the reference's (what the reviewer checks); the method's blindness rule should be checked against every approved definition. |
| 19 | Links, `link-entities` | The "second piece of evidence" rule earned its place immediately: it excluded a Brazilian homonym (Instituto de Ciências → Instituto de Ciencias once accents are removed) and the acronym UK matching a London address. | important (positive) | Keep the rule; add both cases to the skill's examples as the two typical false matches (accent stripping, short acronyms). |
| 20 | Links, `link-entities` | The first linker run left 66 Argentina-text mentions unidentified; reading them by hand showed a normalization bug (non-ASCII dashes removed without a space, gluing words). Fixed: 42 unidentified. No automated check would have caught it. | important | `link-entities`: after every run, read a sample of the **unlinked** records by hand, not only the linked ones; test the normalization on real non-ASCII punctuation. |
| 21 | Links, `link-entities` | The doubtful cases were reviewed by an AI assistant (Claude); the user asked that another assistant (GPT) validate them before a person confirms. The skill has one level («revisado por IA, a confirmar»). | gap | `link-entities`: allow a second, independent review of corrections (another assistant or a person), recorded in the CSV with who reviewed and who validated. |
| 22 | Links, `link-entities` | 56 of the 91 doubtful cases were the acronym «UK» (Universidad Argentina John F. Kennedy) in British addresses. Short acronyms that are also country or state codes (UK, IL, IA) flood the review. | gap | `link-entities`: a list of acronyms that are also common place codes, rejected automatically with a written rule and kept visible, so reviewers spend time on the real doubts. |
| 23 | Links, `link-entities` | Publishers leave HTML entities in affiliation text (`&amp;`, `&#x00E1;` in 33 mentions). They broke the segment split and stayed in normalized text. Found by reading candidates by hand. | gap | `link-entities` and `add-source`: decode markup entities in the single normalization function, and profile them during inspection. |
| 24 | Questions to links, `add-question` and `link-entities` | GPT pointed out that "suspected gap" was implemented as "no identification at all", while cq3 asks about any organization a string names, including strings that also name known ones. | important | `link-entities`: exceptions (gaps, variants) are searched per **named thing**, not per record; zero links per record is not the definition of a gap. |
| 25 | Requirements, lifecycle | After the user approved a new reading of cq2, the requirement file was left unchanged (a side note in the discussion instead). GPT caught that the lifecycle could not bind the new meaning. Fixed by re-proposing and re-approving with the recorded approval. | important | Contracts: a changed business reading always goes back into the requirement file and the lifecycle, never only into a discussion note. |
| 26 | Mapping, `map-source` | `rdfs:range` on `identifies` makes Rastro deduce that every identified organization is Argentine, so a SPARQL check "no identification points to a non-Argentine organization" passes by construction. The real check had to be done on the country (or in SQL). | important | `map-source` and `quality-rules`: a check against a class that a range or domain implies is vacuous; check the underlying value instead. |
| 27 | Questions, `add-question` | Ontop does not support `FILTER NOT EXISTS` inside a `UNION` branch, and `SAMPLE` returns an arbitrary name (nondeterministic answers cannot be checked). | gap | `add-question` watch-outs: use `OPTIONAL` + `!BOUND` inside union branches; use `MIN` (or a display-name property) instead of `SAMPLE` for labels. |
| 28 | Questions, lifecycle | `lifecycle.py validate` imports rdflib; the local Python had an incompatible pyparsing, so validation needed a clean environment. | minor | Contracts: run the lifecycle and verify commands from the project's pinned environment (a documented venv), not whatever Python is installed. |
| 29 | Questions, `add-question` | This is the first domain with a `query-checks.yaml`. Before references exist, the only honest assertions are invariants from the approved definitions (every mention appears; at most 538 organizations). They catch broken queries but say nothing about accuracy. | gap | Contracts: name the two levels explicitly (technical validation by invariants, accuracy validation by references) so a "validated" state is not read as "correct". |
| 30 | Experiment log | A third hand-editing error in the log: an unquoted colon made it invalid YAML. The update failed, but the commit still ran (commands chained with `;`), so a commit went out without its log entry. Caught on the next read and fixed in a follow-up commit. | important | Same as note 7: a command to record sessions; and `close-phase` should refuse to commit when the log does not parse. |
| 31 | Questions, `add-question` and `verify` | `query-checks.yaml` only supports row counts, exact values and one number. GPT showed that `min_rows: 1456` passes with repeated and missing mentions. The real properties (exact key coverage, a bound per row, a candidate established independently) needed a script outside the method, derived from the pinned records. | important | `verify`: support key-set coverage against a source-derived list and per-row column bounds, or name a structural-check script with a receipt in the registry. |
| 32 | Questions, lifecycle | The expectations file is shared by all questions, so editing it for one query (cq3) invalidated the validation of the other two. They had to be revalidated without any change of their own. | minor | Lifecycle: bind each question to its own entry of the expectations file, not to the whole file. |
| 33 | Questions and quality, `add-question` and `quality-rules` | Wording in a query label and a quality rule claimed more than the evidence: «sin nombre en ROR» for a heuristic miss, and a filled decision column read as a review. GPT caught both. | important | Skills: labels for heuristic outputs say «candidato» and the search that produced them; keep «who decided» (AI or person) apart from «a person confirmed» in every reviewed record. |
| 34 | Quality, `quality-rules` and `ontology/calidad.py` | The runner ignores `sh:severity`: the IDEHU warning and the 91 informational findings count as «fallas», and the status is `defects_detected`, the same as an impossible value. The severity is only visible in the rule text. | important | Runner: keep each result's severity, and report a status per severity, so that a person sees at a glance what blocks and what only informs. |
| 35 | Quality, `quality-rules` | A SPARQL constraint with `GROUP BY $this` returned a row for an empty group, because pySHACL pre-binds `$this`. The good example caught it. | gap | `quality-rules` watch-outs: aggregate constraints always need a `HAVING`; the good example is what catches this. |
| 36 | Mapping and lifecycle | Adding three terms that no query uses put all three questions back to «approved» (the lifecycle binds the ontology and mapping). Re-implementing and revalidating them was mechanical. | minor | Lifecycle: bind a question to the terms its query uses, or say in the skill that any dictionary change requires revalidating every question. |
| 37 | Quality, `quality-rules` | One good and one broken example per rule passed while three rules were wrong: a severity in the wrong place, free text accepted as confirmation, a missing status accepted. GPT found them by running each rule alone on extra cases. | important | `quality-rules`: test every constraint of a rule (one broken case per constraint) and assert the reported severity, not only pass/fail; the examples file should allow several broken cases. |
| 38 | Quality, `quality-rules` | A rule's label promised more than it checked («la confirmó una persona» for a string inequality). | important | `quality-rules`: write the label from what the constraint actually tests; if a real check needs data that does not exist yet (who confirmed, when), say the rule only marks what is pending. |
