Fuentes

AACT · ChEMBL · openFDA en Postgres · MeSH en GraphDB. Los datos no se mueven.

Rastro es una capa semántica: se pone entre las tablas y quien pregunta. Para quien sabe SQL, cada pieza tiene un equivalente. La ontología es el esquema de negocio que uno querría tener. Los mapeos son como definiciones de vistas, escritas en un estándar (R2RML). Los enlaces son las claves de join que no existían entre fuentes. SPARQL es SQL sobre conceptos, y Ontop es un compilador que lo traduce a SQL normal sobre las tablas reales.

Sin integración, el LLM adivina qué fármaco nombra cada ensayo, con texto. Con la integración hecha una vez, solo nombra conceptos.

Cruza tres fuentes: el ensayo, el target del fármaco y la jerarquía de enfermedades. Sin integración, el LLM escribió 1.543 caracteres de SQL adivinando nombres en el texto. Con las tablas de enlaces, 571. Con Rastro, 435 de SPARQL, solo conceptos, y Ontop genera el SQL. La gran diferencia la hace integrar una vez; SPARQL la hace un poco más corta y en palabras de negocio.

La comparación honesta. Sin integración, el SQL directo inventa cómo reconocer un fármaco en cada consulta: acierta 18 y cambia de respuesta según cómo se pregunte. Si al SQL le damos las tablas de enlaces de Rastro, acierta todo y es consistente: la precisión viene de integrar una vez. Lo que agrega la capa semántica es el resto: el conocimiento de cada fuente queda en los mapeos y no en cada consulta, cada dato trae su fuente, y se puede consultar junto con datos de otras organizaciones. Una capa de vistas SQL bien hecha resolvería parte de esto; la capa semántica lo hace con estándares y suma procedencia y datos de afuera.

Medido sobre los datos reales. En la app: pestaña «Cuando las fuentes cambian».

Tres cambios que pasan en la vida real. Si la fuente renombra una columna, el SQL se rompe en cada consulta que la usa, con o sin las tablas de enlaces; en Rastro es una línea del mapeo. Si cambia cómo se escribe un valor, el SQL ni siquiera falla: devuelve cero. Y si el negocio cambia una definición, como qué cuenta como terapia dirigida, en Rastro es una línea de la ontología: Ontop la aplica a todas las preguntas. «Terapia dirigida» no tiene ninguna tabla ni mapeo: Ontop la deduce. Honestidad: una capa de vistas SQL también centralizaría parte de esto.

Por qué funciona

Lo difícil se hace una vez, y se revisa

Heterogeneidad de datos

La misma entidad, escrita distinto en los valores

«Pembrolizumab 200 mg»
→ CHEMBL3137343

Lo resuelve el entity linking: crea la clave que falta entre ensayos y fármacos, una vez.

Heterogeneidad de esquema

El mismo concepto, en columnas distintas

query_id · chembl_id · parent_chembl_id
→ Fármaco

Lo resuelven los mapeos: las tres columnas pasan a ser un solo concepto.

Después, Ontop une todo solo: cada pregunta usa la misma definición.

Dos tipos de heterogeneidad, cada uno con su solución. De datos: el ensayo dice «Pembrolizumab 200 mg» y ChEMBL dice CHEMBL3137343; ningún igual de SQL los une, así que el entity linking crea esa clave una vez y se revisa. De esquema: openFDA llama al fármaco query_id, ChEMBL chembl_id y la tabla de enlaces parent_chembl_id; los mapeos dicen que las tres son el mismo Fármaco. La lista completa está en docs/integracion.md.

Límites y próximo paso

Probado: con las tablas de enlaces de Rastro, el SQL acierta igual. El valor está en integrar una vez y en mantener esa integración como una capa estándar.

Cobertura: 81 % de las intervenciones de tipo fármaco enlazadas. Una foto de octubre de 2026, no datos en vivo.

Evaluación: preguntas propias. Las referencias las hizo un asistente de IA; falta la confirmación humana.

Próximo paso: un piloto con datos del cliente sumados a las fuentes públicas

Decir los límites antes de que los pregunten. Lo medimos: si al SQL le damos los enlaces de Rastro, acierta igual. Lo que vendemos es la integración hecha una vez, mantenida en un lugar, con fuente y conectada con datos de afuera. Cerrar con la propuesta de piloto.
